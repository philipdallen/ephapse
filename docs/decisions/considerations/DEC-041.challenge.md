# DEC-041 independent challenge

**Directive:** DEC-041 — adopt the directive-first task protocol, pilot on ephapse.
**Author run-id:** `20260930-1241-q7mx` (deliberately not the memo's

**Proposal text:** `docs/decisions/considerations/DEC-041.proposal.md`
(sha256 `b41df84f82ed362d11bb27079a58c39660be29256ecc312c61f2f1a02db4dbce`,
recomputed this run with `sha256sum`).
**Memo under challenge:** `docs/decisions/considerations/DEC-041.md`.
**The memo's recommendation:** **Option A — full adoption, pilot on ephapse,
`directive_scan.py` warn-only, bake-off branch rule as a named §5 exception.**

The memo is thorough and its evidence table is honest. This challenge is not
written to agree with it — the proposal's §1a says a challenge that only agrees
is treated as missing. It argues a **different option** (B′ below), records
**three conflicts the memo's own searches surface but the memo does not name**,
and names the **cheapest experiment** that would settle the tier question without
deciding it.

## 1. The strongest case for a different option — **Option B′**

The memo offers A (full), B (drop bake-offs), C (do nothing), and picks A. The
strongest case for a different option is **B′: adopt the consideration/memo half,
defer the bake-off half *and* the scanner's issue-level fail rule**, with the
scanner shipping in `report` mode and an explicit grandfather clause.

**Why the bake-off half should wait, not just be guarded.**

- **The memo's own §9 admits the rule has no enforcement point.** "One agent may
  not hold two slots of one bake-off … the rule lives in prose and in the sweep,
  not in the lock." The memo calls this a "limitation of Option A, not a
  blocker." Under the repo's own standard — *"a check that cannot fail is not a
  check"* (`tooling/gates/README.md`, cited by PleaNP #170) — a load-bearing
  isolation rule with **no** machine enforcement is exactly the advisory prose
  the whole directive exists to eliminate. Option A adds the prose and defers the
  enforcement, so it reproduces the defect it was written to fix.
- **Slot branches are the only branch namespace proposed, and the only
  branch-namespace change in this repo since DEC-001.** DEC-001 ("Single active
  branch") is the founding decision; `AGENTS.md` §Branches still says a second
  branch "would be a milestone marker." Section 4 carves out an entire parallel
  branch tree (`bakeoff/<parent>/<slot>`) plus tags (`bakeoff-lost/*`) from a
  repo whose `git ls-remote --heads origin` returns **exactly one** branch
  (`refs/heads/main`, checked 2026-09-30). That is the change most expensive to
  reverse in practice, and it is the half the human's directive mentions last.
- **Bake-offs multiply cost by N and every slot must still fit a 20-minute run**
  (proposal §4). The pilot has 19 open issues, ~1 `status:available` at any time
  (checked 2026-09-30), and a queue that would be *cannibalised* by N-way
  duplication of one task. At current volume the bake-off mode would starve the
  ordinary queue before it proved anything.

**What B′ keeps.** Sections 1 (directive-first), 1a (consideration memo +
challenge + ratification), 2 (decomposition), 3 (blockers-as-decisions), and a
`directive_scan.py` that starts in **report-only** mode. This is the half that
addresses the **observed** failure — DEC-030's "two further issues were filed by
a parallel session during it and one arrived unlabelled." The memo's §12 NEEDS
question already offers to run Tier 2 as Tier 1 "for the first N directives";
B′ is the same concession taken one step further: pilot the cheap half, measure,
then decide on bake-offs with data.

**Cost of B′.** The human's explicit ask for "duplicate work to compare which is
best" is deferred, not met. The memo's §4 Objective-ordered trade-off table
reaches the same conclusion for B and rejects it on that ground. The challenge's
reply: the ask is *met by section 1a alone* (a sanctioned place to compare
approaches is the challenge file), and the bake-off machinery is the part least
proven to help. Deferring it is a scoping decision, and the proposal's own
section 5 requires a DEC for scope cuts — B′ is that proposal, recorded openly,
not a silent one.

## 2. Conflicts the memo missed

The memo's §3 C1–C6 are correct as far as they go. Re-running its searches
against **raw artifacts** (not the memo's summary) surfaces three further
conflicts. All three are in artifacts the memo itself cites.

**C7. The proposal anchors the new gate to `pass_scan.py`, which does not
exist — and the memo wrote a fix that the proposal does not carry.** The memo's
§7 records "`pass_scan.py` does not exist in ephapse … sweep uses
`audit_claims.py`." But the proposal still instructs, at
`DEC-041.proposal.md:96`: *"Add it to the start-of-session sweep next to
`pass_scan.py` (§Claiming step 1a)."* A grep of the live tree confirms the file
is absent and the actual start-of-session tools are
`tooling/claims/claim.py status --run-id <id>` and
`tooling/claims/audit_claims.py --fetch --run-id <run-id>`
(`docs/MULTI_AGENT_WORKFLOW.md:292-293`). **The memo noted the dead reference but
did not feed it back into the proposal**, so if A is adopted the scanner is
wired next to a file that does not exist. This is not a conflict with a DEC; it
is a conflict between the memo and the artifact it is reviewing — and the
protocol's own rule ("Add it to the start-of-session sweep") is unimplementable
against the text as written.

**C8. The scanner's fail conditions would fail the queue it governs, including
this challenge, and the proposal has no grandfather clause.** Section 1 of the
scanner fails when *"a `status:available` or `status:claimed` issue has no
`Directive: DEC-NNN`."* The open-issue census (API, 2026-09-30, `state=open`,
19 issues) shows **only one** issue carries a `Directive:` trailer: #90, this
task. The other 18 — including the DEC-041 memo task itself, if re-filed, and
every auditor finding — carry none. The memo's §6 uses the phrase "grandfather
window" ("Target after the grandfather window: 0") but **the proposal never
defines one**; read literally, the first act of the directive-first scanner is to
flag 18/19 of the live queue as violations. The scanner is specified as
warn-only *for commits* ("warning for the first two weeks") but **not for
issues** — for issues it fails immediately. The memo records the
`flow.open_total` presentation side-effect of Proposed-DEC issues (§10) but not
this, the more direct one: the gate is retroactive on a queue it cannot have
retrofitted.

**C9. The proposal attributes the duplicate-work rule to DEC-026, which is
unrelated.** Proposal §5 (line 338) opens its edit table with *"Duplicate-work
rule (DEC-026, PleaNP §Claiming step 5)"*. DEC-026's actual title —
`docs/decisions/LOG.md:1139` — is *"G-D9/G-D10: an instrument can pass its
cutoff and track the wrong pair"*, a detector-statistics entry with no branch or
duplicate content. The "never push a second copy" rule lives at
`docs/MULTI_AGENT_WORKFLOW.md:436` (§5 concurrent-work rules:
*"Never push a second copy"*), and the one recorded instance of dropping a
duplicate is **DEC-028**, not DEC-026. The edit table's own citation is wrong, so
"amend DEC-026" would amend nothing and leave the real rule at line 436
uncross-referenced. This is minor but it is the kind of stale citation the
memo's §7 exists to catch, and the memo's evidence table does not list it.

## 3. The cheapest experiment that settles it

The real dispute is not "logging: yes or no" — that half is cheap and the memo
and this challenge agree it should land. The dispute is **whether the bake-off
half is affordable.** The memo's §8 flags the scanner task as "borderline, and
likely over" and proposes a split; the same doubt applies to bake-offs, and the
proposal's own falsifier (§6 of the memo) already names the measure: *"more than
3 of 10 `URGENT` overrides would falsify the 'waiting period is affordable'
premise."*

**The cheapest experiment: run the pilot for its first 10 directives with the
bake-off half disabled (B′), and count three things that already exist in the
queue.**

1. `Directive:`-less `status:available`/`status:claimed` issues (the C8 count).
2. `RATIFY … URGENT:` overrides per ratification comment (the memo's own
   falsifier, §6).
3. Directives that reach `Active` with no memo (the memo's §6 target: 10/10).

All three are one `gh api` call each, already scoped by the proposal's
end-of-session report. **If bake-off demand is demonstrated** — a task in those
10 directives with a genuine design fork and two plausible answers — open the
bake-off half then, as a Tier 2 DEC with its own memo. **If not**, B′ is
sufficient and Option A's section 4 was ceremony. This costs zero extra runs
beyond the pilot already budgeted, whereas Option A spends a Tier-2 waiting
period, a scanner build (the memo itself calls it "borderline over"), and a new
branch namespace to settle the same question in the same 10 directives.

## 4. Verdict

Argue for **B′ over A**: the memo's recommendation trades the cheap, observed
problem (undirected work, DEC-030) against an unenforced rule (memo §9), an
unimplementable anchor (C7), and a retroactive gate with no grandfather clause
(C8). The memo is right that "the consideration and logging half is low-cost"
and wrong that the bake-off half is "contained to slot branches" — it is
contained to a branch *namespace* this repo has never had, and to a rule the
lock cannot enforce.

NEEDS: choose the pilot's first-scope — (a) Option A as the memo recommends, or
(b) B′: adopt sections 1, 1a, 2, 3 with a report-only scanner and an explicit
grandfather clause, and defer section 4 (bake-offs) to a second Tier-2 DEC if
the first 10 directives show demand. This is an owner decision; the memo's §12
NEEDS line asks the adjacent questions (Tier-2 waiting period, `flow.open_total`)
and this one should be answered alongside them.
