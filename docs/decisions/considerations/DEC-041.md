# DEC-041 consideration memo

**Directive:** DEC-041 — adopt the directive-first task protocol, pilot on ephapse.
**Proposal text:** `docs/decisions/considerations/DEC-041.proposal.md`
(sha256 `b41df84f82ed362d11bb27079a58c39660be29256ecc312c61f2f1a02db4dbce`).
**Status of the DEC:** `Proposed`. This memo recommends; it does not decide.
**Evidence rule:** every claim below cites a file, a commit SHA, or an API
result. Anything I could not check is marked `unverified`.

## 1. Direction restated

The human wants (a) a decision logged by the top-level agent *before* subtasks
are created, (b) a research-and-consideration step so a directive cannot be
launched without thought, (c) sanctioned duplicate work where several agents
attempt the same task and only the judged winner merges, and (d) the pilot run
on ephapse. Verbatim source, with the three quotes, is in `LOG.md` DEC-041.

## 2. Why now

The repo already has most of the pieces the directive formalises, so the marginal
cost is low and the marginal clarity is high:

- Decisions exist (`docs/decisions/LOG.md`, 40 entries before this one) but
  nothing ties an issue to the decision that justifies it. No issue in the open
  queue carries a `Directive:` trailer (`GET /repos/philipdallen/ephapse/issues`,
  open set, 2026-09-30).
- The commit trailer convention already exists in spirit: commits carry
  `Refs:`/`Run-id:`-style trailers (e.g. `8cfb928`, this run's DEC commit).
- The failure this guards against is on the record: DEC-030 measured the tree
  drifting *while the analysis was written* ("two further issues were filed by a
  parallel session during it and one arrived unlabelled"). Work arriving without
  a decision behind it is the observed failure mode.

If we wait a week: the queue keeps growing under the current labels, and the
`Directive:` field would have to be backfilled for every issue filed in the
meantime, which is exactly the "logged-late" state the protocol wants to make
visible rather than normal.

## 3. Conflicts

Searched `docs/decisions/LOG.md`, `docs/MULTI_AGENT_WORKFLOW.md`,
`docs/AGENT_HANDOFF.md`, the open issue queue (API, 2026-09-30), and
`git log origin/main`. Searches run: `grep -nE "^## DEC-"`, `grep -n
"single active branch|one branch|commit directly|no feature branches"`,
`grep -n "duplicate|second copy"`, plus the open-issue label census.

**C1. The `main`-only rule versus bake-off slot branches (known, real).**
DEC-001: "Development happens on one branch, `dev`. No feature branches, no PRs
for routine work." `MULTI_AGENT_WORKFLOW.md` §5: "Commit directly to `main` (no
PR)." The protocol's section 4 puts each bake-off slot on
`bakeoff/<parent>/<slot>` and says that is "the one exception to the
commit-to-main rule." This is a direct contradiction, resolved by section 5 of
the protocol (amend the rule with the slot-branch exception). Note DEC-001 still
names the branch `dev`, which is stale — `AGENTS.md` §Branches and `OPERATING_
CONTRACT.md` both record the rename to `main` (2026-09-22). The protocol should
be worded against `main`.

**C2. Duplicate-work rule.** `MULTI_AGENT_WORKFLOW.md` §5: "Never push a second
copy." The protocol's section 4 is the sanctioned exception. Section 5's edit
table already covers this; no other DEC forbids duplicates.

**C3. Claim tooling versus bake-off slots.** DEC-031 makes the git-ref CAS the
authoritative lock, one `claims/<issue>.claim` per issue. Slot issues are
ordinary issues, so the lock works per slot. The protocol's "one agent may not
hold two slots of one bake-off" is *not* something `claim.py` enforces (see §4).
No conflict with DEC-031, but the new rule has no enforcement point.

**C4. Label vocabulary.** `MULTI_AGENT_WORKFLOW.md` § Task states lists
`status:*`, `priority:high`, `needs-review`. The protocol adds `bakeoff` and
`needs:human`. `needs:human` is referenced in the protocol's blocker section but
the label does not exist in the repo (labels API, 2026-09-30). No conflict, an
addition.

**C5. Decision-log status vocabulary.** Current entries use `adopted` /
`Superseded`. The protocol adds `Proposed` and `Rejected` and a new
`docs/decisions/considerations/` directory. `LOG.md`'s own header says "Entries
are append-only — supersede rather than edit", which the protocol preserves. No
conflict.

**C6. Gate-count and single-source discipline (interaction, not conflict).**
DEC-039 makes gate counts single-sourced via `gate_inventory.py`. The protocol
adds a *new* gate (`directive_scan.py`), which must not be counted by hand in
prose — it should be added to the inventory table so DEC-039's rule keeps
holding. Flagged so the implementation does not re-open #38/#88.

No conflict found with the sizing rule, the emergent-requirement rule, or the
`<!-- oh-agent -->` marker; the protocol explicitly leaves those unchanged.

## 4. Options

**Option A — full adoption as proposed (directive-first + consideration +
bake-offs).** Cost: one memo per Tier 1/2 directive, one challenge per Tier 2, a
24-hour wait on Tier 2, and a new warn-only gate. Makes easier: auditable
direction-to-task lineage; a forcing function against launching a half-formed
directive; a sanctioned path for genuine design competitions. Makes harder:
every Tier 2 directive pays a day of latency, and the `URGENT` override exists
precisely because that cost is sometimes wrong.

**Option B — adoption without bake-offs.** Adopt sections 1, 1a, 2, 3 and the
scanner; drop section 4. Cost: none of the duplicate-work machinery, no slot
branches, no judge role. Makes easier: no contradiction with DEC-001/§5's
single-branch rule, so the riskiest part of the change (a second branch
namespace) is deferred. Makes harder: the human's explicit ask for "duplicate
work to compare which is best" is unmet. This is the narrowest option that still
delivers the *logging and consideration* half of the directive.

**Option C — do nothing.** Cost: none now. Makes harder: nothing changes, so the
unlabelled/undirected work DEC-030 measured continues, and the human's request is
not met. Recorded for completeness, not recommended.

**Recommendation: Option A, with two guardrails.** (i) The `directive_scan.py`
gate ships **warn-only** (`--strict` opt-in) and is added to the sweep as an
advisory line, so it cannot block the queue before its own fixtures prove it can
fail. (ii) The bake-off branch exception is written as a named exception in §5,
not a silent second branch policy, so DEC-001's intent (no branch sprawl) stays
readable. Section 6 of the protocol is right that this does not prove human
authorship or make anyone think; it makes the ordering checkable, which is the
achievable part.

## 5. Reversibility

Reversible at low cost for the pilot, because the pilot is scoped to ephapse and
the artifacts are additive:

- The DEC can be `Superseded` by a later entry; the log is append-only so the
  history survives.
- `directive_scan.py` is warn-only, so removing it strands nothing.
- If bake-offs are never used, no slot branches exist to clean up; the `bakeoff`
  label is inert.

What would be stranded by a reversal: issues filed with a `Directive: DEC-041`
trailer and any bake-off `bakeoff-lost/*` tags. Both are cheap to leave in place
(the trailer is just text; the tags are the record of what was considered).
Nothing is deleted, so the reverse is "stop enforcing", not "undo".

## 6. Falsifier

The pilot's success test, made observable so it can be counted over the next N
directives (proposed N = 10):

- **Reached `Active` with a memo:** every Tier 1/2 directive that reaches
  `Active` has a `considerations/DEC-NNN.md` with all eight headings. Target:
  10/10. If any reaches `Active` without one, the scanner failed its purpose.
- **Rejected or amended at consideration:** count of directives that were
  `Rejected`, or superseded by a new `Proposed` DEC, *before* any task was
  filed. A high count is the consideration step working; **0 over 10** would mean
  it is a rubber stamp.
- **`URGENT` overrides:** count of Tier 2 ratifications that used `URGENT:`. A
  high count means the 24-hour wait is mis-sized for this portfolio; **more than
  3 of 10** would falsify the "waiting period is affordable" premise.
- **Directive-less work:** count of `status:available`/`status:claimed` issues
  with no `Directive: DEC-NNN`. Target after the grandfather window: 0.

The decision was wrong if a directive reaches `Active` with no memo, or if the
override/rejection counts show the ceremony is either ignored (0 rejections, many
overrides) or purely obstructive (many rejections of directives the human then
re-issues unchanged).

## 8. Run cap

The brief asks whether the memo, challenge, and scanner tasks each fit the
20-minute sizing rule.

- **Memo task (this one):** fits. A reading-and-writing task with no model or
  network dependency beyond the GitHub API; it produced this file in one run.
- **Challenge task:** fits by construction — it re-runs the same searches and
  writes one file, and it must be a *different* run for independence.
- **Scanner task (`directive_scan.py`):** borderline, and likely over. It mirrors
  existing gate scripts (`validate_experiments.py`, `check_docs_coherence.py`),
  supports a `--strict` flag, and ships a self-test proving each check can fail —
  a code change plus a fixture pair plus a test. The protocol already separates
  the scanner from the memo and challenge, so if it overruns it should be
  **split** (scan logic first, self-test fixtures second), not checkpointed.
  Flagged for the implementation run.

## 9. Claim compatibility

The brief asks whether `claim.py` works for bake-off slot issues, and whether it
can enforce "one agent may not hold two slots of one bake-off".

- **Per-slot claiming works.** `claim.py` keys entirely on
  `claims/<issue>.claim` (`claim_path`, `tooling/claims/claim.py`), and each
  bake-off slot is its own issue. So the git-ref CAS takes and releases a lock
  per slot exactly as it does for any issue. No change is needed for the lock to
  work on slots.
- **The "one agent, two slots" rule is *not* enforceable by `claim.py` as it
  stands.** The tool has no notion of grouping — it cannot see that two issues
  belong to the same bake-off. It enforces "one claim per run-id per issue", not
  "one claim per run-id per parent". Enforcing the bake-off rule would require
  either (a) reading the parent's slot list and refusing a second live claim by
  the same run-id, or (b) a scanner check. The brief forbids changing `claim.py`,
  so this is a **gap**: the rule lives in prose and in the sweep, not in the
  lock. Recorded as a limitation of Option A, not a blocker. It also interacts
  with `MULTI_AGENT_WORKFLOW.md` §Claiming step 4c, which verifies ownership
  *per issue* only.

## 10. Labels and metrics

The brief asks whether the new labels (`bakeoff`, `needs:human`) or Proposed-DEC
issues change any field in `hub_sweep.py` output as defined in
`METRIC_CONTRACT.md`. **They do not change any field definition:**

- `flow.open_total` counts *all* open issues — unaffected by new labels.
- `flow.wip` counts `status:claimed`; `flow.available` counts `status:available`
  — both key on `status:*`, which the new labels are not.
- `flow.needs_review` counts `needs-review`/`review:*` — unaffected.
- `flow.blocked`/`janitorial` key on `status:blocked-needs-input` plus
  `on-hold`/`auditor:*` — unaffected.

Verified against `hub_sweep.py`'s `build_flow` and `build_notes` and
`METRIC_CONTRACT.md` §Field definitions. **Caveat to record, not fix:** a
Proposed-DEC *issue* is an open issue, so it *does* raise `open_total` and
therefore lowers `blocked_ratio` — the same "the population moved" effect the
contract already documents for the W4 boundary. That is a presentation artefact
of counting open issues, not a definition change, and it is not something to fix
here; whether consideration issues should be excluded is an owner decision, which
the contract reserves to the owner. So this is an **owner decision if it matters,
not a fix**.

## 11. Known weakness

Stated plainly, as the brief requires: all agents authenticate as one GitHub
account (`philipdallen`; DEC-031 records the same fact). A `RATIFY DEC-NNN`
comment is therefore *not* provably authored by the human. The only
distinguishing signal is the **absence** of the `<!-- oh-agent -->` marker that
every agent comment carries. This is a convention, not a cryptographic proof: an
agent that omitted the marker, or a human reusing an agent-style comment, would
break it. The protocol's section 6 says this outright; this memo confirms it is
accurate and cannot be fixed by the protocol as written.

## 12. Recommendation and open question

**Recommendation: Option A (full adoption), pilot on ephapse, with the
`directive_scan.py` gate warn-only and the bake-off branch rule written as a
named exception to §5.** The consideration and logging half is low-cost and
addresses an observed failure (DEC-030); the bake-off half is the human's
explicit ask and is contained to slot branches.

NEEDS: confirm two things before Phase 2 flips DEC-041 to `Active` — (1) is the
24-hour Tier 2 waiting period affordable for this portfolio, or should the pilot
run it as Tier 1 (memo, no wait) for the first N directives; and (2) should
consideration issues be excluded from `flow.open_total` so a Proposed DEC does
not move the published `blocked_ratio`? Both are owner decisions, not agent ones.
