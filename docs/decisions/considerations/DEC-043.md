# DEC-043 — Consideration memo

**Decision:** RLM Analyzer triage decisions for ephapse (see `docs/decisions/LOG.md` § DEC-043).
**Class:** Tier 1 — task protocol. It changes how findings become tasks, not how results are produced.

## 1. Direction restated

The owner asked that triage findings from the RLM Analyzer pass be verified against
the repositories and turned into pickup-ready task files, with the required decisions
logged before any task is created. This memo records the five decisions that govern
that conversion, so each filed task cites a logged decision rather than a chat message.

## 2. Why now

The RLM Analyzer reports are now available for all five public repos. Filing tasks
directly from an LLM report would put unverified claims into the work queue, which is
the failure mode the integrity gates exist to catch. The decisions below are the
gate between report and queue, so they are logged before the first task is filed.

## 3. Conflicts

- **With the analyzer's own confidence.** The reports are phrased with high confidence
  on some findings that are factually wrong for this repo (see § 7). D1/D2 resolve this:
  the report is a lead, not evidence.
- **With "file everything" convenience.** Filing all findings would inflate the queue
  with refuted items. D4 resolves this: only verified findings get a task.
- **With the security skill's generic checklist.** Its web-app controls (authn/authz,
  API validation, headers, WAF, pen testing, SAST/DAST, log anomaly detection) assume a
  running service. This repo has none, so D3 scopes them out rather than filing
  no-op tasks.

## 4. Options

- **Option A (chosen).** Verify each finding against raw files; file one task per
  verified finding; record refuted findings in the summary. Log the decisions first.
- **Option B.** File every finding as a task and let workers re-verify. Rejected: it
  moves the triage cost into every future run and admits known-false items.
- **Option C.** File nothing and hand the report to the owner. Rejected: the owner
  asked for pickup-ready tasks, and verified findings are actionable without a human
  decision.

## 5. Reversibility

Fully reversible. The decision is a filing policy; it writes task files and one DEC.
Reverting means closing the tasks; no code, gate, or artifact changes.

## 6. Falsifier

This decision is wrong if a filed task turns out to rest on a finding that raw-file
inspection does not support. That would mean D1's verification step was skipped or
done wrongly, and the task should be closed as invalid with the gap recorded.

## 7. Evidence

Verification was done by reading raw files in this repo, not by trusting the report.
Findings confirmed: a large artifact set is committed to git with no LFS/ignore; the
new `directive_scan.py` gate is registered as `G-M4` with a live-queue fixture and
24/24 gate tests passing; no `dependabot.yml`; experiment result JSONs carry only
numeric summaries with no model output. Findings refuted: the report's web-service
security items (no service exists), and its claim of uncommitted experiment data
(the results JSONs are tracked).

## 8. Recommendation and open question

Recommendation: adopt Option A. Verify each RLM finding against raw files, file
one task per verified finding, and record refuted findings with their evidence.
The verified set for ephapse is small (one task: the missing `dependabot.yml`),
which is itself the argument — the report's headline items were either
web-service security advice that does not apply or claims already covered by the
auditor.

`NEEDS: ratify DEC-043 (Tier 1 filing policy for the RLM triage pass).`

## 9. Run cap

Filing only. No code is changed. The work is bounded by six repos and the verified
finding count, and completes within a single triage run.
